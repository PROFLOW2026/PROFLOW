## 1. Domain Architecture Summary

### Data Model (what tables exist)

| Table | Purpose | Key Columns |
|---|---|---|
| `employees` | Master employee record | `id, organization_id, name, status, hire_date, end_date, employment_basis, standard_hours_per_day` |
| `rate_versions` | Date-effective compensation rates | `employee_id, valid_from, valid_to, base_rate, rate_unit (hourly/daily/monthly), burden_percent, working_days_per_month` |
| `labor_cost_components` | Additive cost items per rate | `rate_version_id, basis (amount/percent), amount, percent` |
| `attendance_days` | Clock presence per employee/date | `employee_id, work_date, status (open/complete/void)` |
| `attendance_events` | Individual clock events within a day | `attendance_day_id, event_type (clock_in/clock_out/break_start/break_end), occurred_at, source, voided_at` |
| `time_entries` | Project/non-project hours (labor Actual driver) | `employee_id, work_date, hours, kind (project/non_project), project_id, approval_status, status (recorded/void), cost_amount` |
| `timesheets` | Weekly (Sun-Sat) approval envelope | `employee_id, period_start, period_end, status (draft/submitted/approved/returned), locked_at` |
| `employee_month_costs` | Monthly employer cost pool (MONTHLY employees) | `employee_id, year_month, estimated_amount, actual_amount, known_quality (estimated/actual), status (draft/applied/closed)` |
| `labor_allocation_runs` | How monthly pool splits across projects | `employee_month_cost_id, method, allocated_amount, unallocated_amount, status (draft/applied)` |
| `labor_allocation_run_lines` | Per-project allocation amounts | `run_id, project_id, amount, percent, basis_hours, basis_days` |

**Critical design point:** Attendance and time entries are intentionally separate domains.  
`attendance_days` = clock presence (never creates labor Actual).  
`time_entries` = approved hours = labor Actual.

### Approval Lifecycle

```
Time Entry: draft → submitted → approved | returned → submitted → approved
Timesheet:  draft → submitted → approved | returned → submitted → approved
```

Labor Actual requires: `time_entries.status = 'recorded'` AND `approval_status = 'approved'`

### Multi-Project Same Day

✅ YES — an employee can have multiple `time_entries` rows for the same `work_date`, each pointing to a different `project_id`.

### Hours Calculation

Reported hours per employee per date = `SUM(time_entries.hours)` where `status='recorded'` and the entry is in scope. See `sumRecordedDailyHoursForPairs`.

### Missing-Day Storage

❌ Absent days are NOT stored. Only days where clock events occurred have `attendance_days` rows. If employee didn't report, there is NO record. The system has no sentinel "absent" rows.

## 3. What Works Correctly ✅

| Area | What Works |
|---|---|
| **Monthly accrual (open month)** | Correctly pro-rates: `P × min(accruedDays, W) / W`. Does NOT assume full month for current month. Future months are skipped. |
| **Daily cost conservation** | `allocateConservedAmountByHours` guarantees `Σ allocated + unallocated = daily pool` exactly (rounding residue on last bucket). |
| **Monthly pool conservation** | `allocateMonthlyRecognizedPoolByWorkDays` conserves recognized pool across day units and then across projects. |
| **Month close immutability** | DB trigger (0037) + `assertMonthOpenForRewrite` prevents silent rewrites of closed periods. Closed-period corrections use `createClosedPeriodSourceCorrection` (audit trail preserved). |
| **Void + replace corrections** | Approved time entries cannot be edited in place. `correctTimeEntry` voids original, inserts replacement with `corrects_entry_id` link. Audit trail preserved. |
| **Employee self-scope** | Employees with ATTENDANCE_SELF or TIME_SELF permissions can only see/edit their own records. |
| **Excess hours tracking** | Daily summaries compute excess vs standard framework hours. Excess requires separate approval. |
| **Burden percent + components** | `LaborCostComponentRecord` supports flat amounts and percent-of-base additive components. Fully loaded employer cost is correct. |
| **Mid-month rate changes** | `calculateMonthlyEmployerCostPoolForMonth` prorates by calendar days when rate changes mid-month. |
| **Attendance overwrite protection** | Any existing attendance in a date range requires `overwriteConfirmed=true` (double UI approval). Single-transaction rollback on any failure. |
| **Attendance-project sync** | When owner applies bulk attendance with project, `syncProjectWorkFromAttendance` auto-creates and auto-approves time entries in the same DB transaction. |
| **Completeness checklist** | 9 completeness checks at month-close covering: missing employer cost actual, unallocated employee cost, incomplete attendance, open time corrections, and more. |
| **Idempotent cost recompute** | `recomputeMonthlyEmployeeCostForOpenMonth` and `recomputeDailyEmployeeCostForDate` are safe to call multiple times. Applied runs are superseded cleanly. |
| **Employer cost in labor Actual** | Burden percent and components are included in the employer cost pool used for project allocation. Social-security-equivalent costs flow through. |
| **Unallocated labor tracking** | `__non_project__` bucket captures admin/unassigned days. Visible in `labor_allocation_runs.unallocated_amount`. Completeness check flags it. |
| **forCosting filter** | Only `status='recorded'` AND `approval_status='approved'` entries contribute to labor Actual. Draft/submitted/returned never create cost. |
| **Duplicate draft prevention** | `planExactDuplicateDraftRemovals` detects and cleans up exact duplicate draft entries. Banner on time page alerts manager. |

## 5. Labor Cost Calculation Summary

| Employee Type | How Cost Is Calculated | Open Month? | Bug? |
|---|---|---|---|
| HOURLY | `hours × loaded_hourly_rate` snapshotted per entry at log time | N/A (per-entry) | ✅ None |
| DAILY | `1 day pool` distributed across day's entries by hours ratio | N/A (per-day) | ⚠️ LAB-007 (incomplete logging) |

**Is there a "1 hour = full month cost" bug?** NO — for monthly employees, `time_entries.cost_amount` is NULL (kind='monthly_allocation'). The monthly pool is allocated via a separate `labor_allocation_runs` mechanism, not per-entry. The cost only flows to projects through the approved entries as a WEIGHT signal, not as a direct cost. This design is correct.
